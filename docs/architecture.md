# Architecture and recovery

Implementation notes for contributors. For everyday operations, see the [user guide](user-guide.md). For source layout and development checks, see [CONTRIBUTING.md](../CONTRIBUTING.md).

## Wallet connections and session credentials

Wallet discovery, connector account events and chain switching use wagmi. Both connection buttons connect directly when one browser wallet is available, or open the same wallet-selection interface when several are available. Announced wallet icons are used when valid; the unnamed legacy Browser wallet entry is not displayed.

The existing lazy WalletConnect provider is adapted to a wagmi injected connector to preserve mobile namespace account resolution and explicit pairing. Injected-wallet connection attempts stop waiting after 45 seconds and restore page controls. An unresolved request blocks another connection attempt to that wallet until it settles; other wallets remain available. Reload after restarting an unresponsive extension. A late response does not sign the user in automatically. WalletConnect pairing keeps its existing interactive wait.

Synapse React resolves the owner signing client; when a late response changes wagmi’s current connection, the selected connector is passed explicitly to wagmi instead. TanStack Query scopes and deduplicates storage configuration, wallet snapshots and pending receipt reads. Session-key persistence, permission lifecycle, bounded transaction recovery, dataset reuse and CAR/IPNI orchestration remain application logic.

You can revoke this browser's key from Wallet setup, or manage authorizations in Filecoin Pay Console. Disconnecting the wallet does not revoke its key.

Session credentials are stored in IndexedDB, encrypted using a non-exportable AES-GCM wrapping key. Tabs on the same origin reuse the latest key under a short wallet/network-scoped lock, synchronize changes, and reread the vault when returning to the foreground. A completed revocation only clears the matching session revision. The application origin can still use those credentials; this does not provide protection against malicious scripts on the origin.

## Datasets, storage copies and upload metadata

The Runway display uses filecoin-pin’s SDK-based account summary and follows Filecoin Pay Console labels. It is fetched separately when the wallet panel mounts; a failed read does not block funding or uploads.

New datasets carry `source: filecoin-drive` metadata. Known datasets are reused for uploads only when their on-chain source matches; older or differently marked datasets remain available for existing-file operations. If SDK resolution fails, Drive checks liveness with the SDK and skips only datasets confirmed non-live on-chain, preserving other candidates and historical files. Successful resolution adds no extra liveness read. Metadata/RPC failures with live or unknown liveness stop the upload rather than clearing candidates or creating replacement datasets.

Each ordinary upload targets two storage copies on different providers. Matching datasets are reused, and missing copies are selected before the funding quote. A previous one-copy upload does not reduce the target for later uploads or trigger replication of existing files. An upload can still finish with fewer copies if another provider is unavailable or fails; the next upload tries for two again. Confirmed copies are saved, including when only a secondary provider succeeds, and the directory's copy count reflects the successful copies.

Each new upload records its original filename as `label` and its normalized folder path as `path`. The top-level upload name and its normalized destination path must fit 96 UTF-8 bytes independently, including extensions and path separators; oversized values are rejected before packing or storage requests, never silently omitted. The IPFS root CID occupies the third piece metadata slot. Imported CARs use `carPath` instead of `path` to preserve both their folder and original-archive download mode within the three-key limit. Names, paths and content identifiers are publicly visible in upload events and the index. Repeated uploads can keep separate file records; deleting shared content affects all matching records, as explained before deletion.

## Discovery and directory persistence

Drive reads [the public Filecoin API](https://api.filecoin.io/docs) by wallet and network on connection, including when this browser has no remembered dataset IDs. It paginates the wallet's datasets, selects `source: filecoin-drive`, and reads their pieces and provider details. It checks each selected dataset's scheduled removals using the SDK, because the index exposes completed removals but not the pending queue. **Load from Filecoin** retries discovery as indexing catches up. File discovery does not wait for wallet balances, payment approvals or session authorization. An empty cache shows a loading state until the first index request completes; failed requests show a retry action rather than an empty-directory message. The API is a third-party index, not proof that a provider is reachable.

The browser caches file records and pending upload/deletion checkpoints in localStorage. Cached files appear immediately. Indexed records merge by dataset/piece identity; missing records in a lagging response never delete local records. Local removal receipts remain authoritative, and explicit indexed removals/chain removal queues keep acknowledged copies hidden. Active and acknowledged historical copies are not paired into a new file record. Locally running storage deletions show **Deleting**. When no local deletion task is running, unfinished copies show **Deletion pending** only if each has an unconfirmed checkpoint and no remaining batch. Other unfinished deletion work shows **Deletion incomplete**, with per-copy queue/receipt status. Once every copy is scheduled or removed, the normal list hides that record. The queue reports Piece IDs, not a progress percentage or guaranteed completion time. A different browser can still see stale state until the chain and index catch up. API or chain-read failures leave the cache intact and report an error instead of treating the wallet as empty.

Connect the same wallet on another browser to discover indexed Drive files without importing a directory. Recent unindexed uploads may initially be absent there. Recovered names prefer legacy `name` metadata, then `label`; missing names display the IPFS root CID, then Piece CID, without storing the fallback as a real name. Missing paths recover at the root. Existing local names, paths and checkpoints are preserved. Older datasets marked `filecoin-pin` are not automatically classified as Drive datasets, but their cached records remain available. Historical local edits cannot be recovered by another browser. Recovered dates use the indexed add-piece epoch and the SDK’s epoch-to-date conversion, so they reflect storage confirmation rather than the original browser upload start. Recovering these dates does not require per-file block reads. CAR archive sizes use the indexed raw size.

For ordinary files with unknown size, at most two concurrent workers read raw IPFS root blocks from recorded providers. Each worker may try multiple providers. Reads have an 8-second timeout per provider, a 2 MiB cap and CID hash verification. UnixFS metadata gives multi-block file sizes without fetching child blocks. Failed size reads keep Unknown and never block file discovery; known local sizes and dates are preserved. Upload transaction hashes remain omitted when unavailable.

File and checkpoint writes use wallet/network-scoped Web Locks to merge against the latest records across tabs on the same origin. Tabs reread the cache when visible, focused, resumed or restored from the page cache; these local resume reads do not query the chain. Wallet/network changes abort discovery and ignore late responses. Directory import/export, local rename/move controls and standalone empty-folder creation/deletion are no longer exposed.

## Upload checkpoints and recovery

Writes require Web Locks over HTTPS or localhost. If a cache save fails, keep the page open, free browser storage and retry saving. Unsaved upload/deletion checkpoints remain in memory and merge with the latest cache on retry. Upload details offer **Retry saving** to persist confirmed file metadata without uploading again. Once a provider acknowledges receipt and the piece-CID checkpoint is saved, the file can be downloaded and another upload can start.

The list and details share Waiting, Uploading, Confirming, Stored, Upload interrupted and Upload failed statuses; Stored means at least one confirmed copy, with outstanding-copy progress shown separately. Indexing, provider receipts and technical steps stay in expandable upload details. Each file has its own upload status and expandable details; replication, indexing and provider confirmation continue in the background. Share and Preview wait for storage processing to finish. Keep the tab open while background upload work is running. Closing file details does not cancel a running deletion; keep the browser tab open.

Uploads save confirmed copies locally even if later replication or IPFS indexing fails. After reload, saved tasks check existing provider operations without resubmitting uploads. Eligible saved tasks are checked at 30-second intervals while visible, up to 20 checks per task; **Check status** also refreshes the Filecoin index and remains available afterwards. Refreshing the page stops browser-side replication, submission and indexing work that has not finished. When submission receipts are missing and no unresolved submitted transaction remains, recovery marks the upload interrupted; if another provider still has an unresolved transaction, it remains pending; status checks can discover existing indexed confirmations but cannot resume those unfinished steps. Transfers interrupted before a receipt was saved require selecting the file again; timeouts alone do not authorize a new upload. The upload network is fixed when the operation starts. After local storage is cleared, the API can recover indexed records; unindexed work and historical local-only metadata cannot be reconstructed immediately. Content is not encrypted.

## CAR imports and downloads

Standalone file downloads retrieve and validate the CAR from a recorded provider, then extract the UnixFS file in the browser. Downloads of individual files inside uploaded folders first try verified IPFS block reads, with a fallback to downloading and unpacking the parent CAR. Folder downloads produce ZIP archives.

Uploads inspect file contents to detect CAR archives regardless of the filename extension. Ordinary files retain the existing UnixFS packing. A detected CAR is stored byte-for-byte without wrapping it in a new file DAG, preserving its root CIDs. Drive uses the first root as the primary CID when an archive has multiple roots. Rootless archives and archives missing a declared root block are rejected before storage requests; the browser directory and content locks require a real primary root.

Imported archives appear as one file record and download as the original CAR bytes from a storage provider. Drive does not expand their internal folders into the browser directory. Single-file previews and IPFS gateway file downloads are omitted for these records: traversing one root cannot reproduce an archive’s other roots or extra blocks. New CAR uploads preserve their download mode through `carPath` metadata, so another browser can recover it. Older CAR records without that field retain their mode only in existing browser caches.

## Deletion checkpoints and content locks

Deletion resolves every matching piece instance across all pages. Providers accept batches of at most 35 removals per dataset, with a queue that drains at the next proving period. Larger removals retain their progress and show **Continue deletion**; retry when the queue has space. Local checkpoints preserve unfinished batches. Once every recorded copy is acknowledged as scheduled or removed, through a confirmed local checkpoint with no remaining batch or a chain-reported queued/completed removal, the file is hidden from the normal list, search and count. Its metadata and transaction receipts remain in the browser cache. Partial removals stay available to continue. Archived receipts are preserved and are not reused to settle a later upload of identical content; pending transactions are checked before submitting another deletion.

Uploads and deletions of different content can run together. Uploads acquire the existing content lock after packing, before storage requests, and hold it through confirmed metadata persistence; the same content cannot be uploaded and deleted concurrently. Deleting a legacy record without an IPFS root CID excludes all uploads for that wallet and network. Wallet switching and session changes in the tab running these operations stay locked until both operations finish. Only one tab can delete the same content for a wallet and network at a time. Another tab reports that deletion is already in progress; after it finishes or fails, **Continue deletion** reads the latest saved checkpoints. This operation lock is separate from the short directory-save lock. Receipts update only their dataset and do not overwrite a newer transaction when a failed save is retried.

These browser locks do not coordinate other devices, browser profiles or CLI clients. An unfinished recorded deletion must be continued before uploading the same content again.

Saved pending deletion receipts are checked without submitting new removals or requiring session authorization. While the page is visible, checks run every 30 seconds for up to ten minutes per observed transaction in the current view, with two content groups checked concurrently. Reloading restarts that window; returning to the foreground permits another check. Manual continuation is blocked during the automatic-check window and while a check remains in flight. Unsubmitted batches require an explicit continuation.

See [deletion recovery](../src/hooks/use-deletion-recovery.ts) and [status mapping](../src/utils/upload/file-status.ts).

## IPFS indexing checks

Pending IPFS root CIDs receive at most five additional background indexing checks, two minutes apart. The browser saves the attempt count and cooldown per wallet/network and CID, so reloads and reconnects do not restart the budget. Checks pause while the page is hidden. When the budget is exhausted, indexing failure does not change a stored file’s main status to a failure or add an indexing suffix. For records with no upload checkpoint or a completed upload, and no deletion state, file details expose the stopped-check notice and **Retry indexing checks** under **IPFS indexing** to start another bounded round. This checks root-CID discoverability in IPNI, not full-file retrieval or replica health.

## Wallet transaction recovery

Wallet authorization, revocation, deposits and storage-payment approvals retain their submitted transaction hash per wallet/network until the outcome is known. A confirmation timeout leaves the operation pending and blocks duplicate wallet setup submissions. After the initial wait, visible pages check every 30 seconds for up to ten minutes from submission. Returning to the foreground or selecting **Refresh status** performs another read, including after that automatic window ends. Reloading restores pending work. Revoking a session also clears the termination permission granted by older versions; renewing it with fewer permissions does not revoke an existing grant. Session authorization also checks the actual permissions and requested expiry; revocation checks that all storage permissions are inactive. This can recover session changes when a wallet replacement changes the transaction hash. Missing receipts and RPC failures are never treated as proof of failure. Payments require a successful receipt.

Pending records also retain the original Filecoin message CID when the node can resolve it from the submitted hash. Recovery first checks the ordinary Ethereum receipt. If that receipt is missing, Lotus `StateSearchMsg` searches at most 120 recent epochs (about one hour) with `allowReplaced` enabled, allowing an otherwise identical gas-repriced message to supply the execution receipt. Exit code zero confirms success; a nonzero code reports failure. Lotus’s explicit call-changing replacement error clears the pending operation with a cancellation/replacement notice and never counts as payment success. A returned message CID is converted to an Ethereum hash for transaction links when available; a failed hash conversion does not invalidate the native execution receipt.

Unsupported Lotus methods, missing original-message data, rate limits and unknown responses leave the outcome unresolved rather than inferring it from a nonce or balance change. Recovery does not search historical account nonces or enumerate blocks. Older pending hashes remain restorable without the obsolete nonce-recovery metadata.

## Folder content cache

Folder listings are cached in IndexedDB by root CID, path and page. The bounded cache contains names, CIDs and sizes, not file bytes, and survives reloads. New uploads seed it from the packed CAR; uncached pages are read and verified from storage providers before caching. Provider failures do not erase cached pages. The cache can be evicted under its capacity limits or cleared with site data; file downloads still need retrievable content.
